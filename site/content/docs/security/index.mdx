## What the relay never sees

The single design constraint everything else follows from: the relay
is untrusted infrastructure, not a trust anchor. It stores and
distributes ciphertext, signed metadata, and wrapped keys — never a
plaintext environment value, and never an unwrapped encryption key. A
fully compromised relay can affect availability and can leak metadata
(which devices exist, when a push happened, how many keys an
environment has) — it cannot, if the client-side cryptography holds,
read a single secret value.

## The cryptography, specifically

<Available>the primitives below are read directly from `keyit-protocol`'s encryption and signing code, not summarized from the design docs</Available>

| Purpose | Primitive |
| --- | --- |
| Device signing (proving a device authorized an action) | Ed25519 |
| Device key agreement (wrapping environment keys) | X25519 |
| Environment payload encryption | AES-256-GCM, random 96-bit nonce per encryption |
| Key wrapping (environment DEK → per-device) | X25519 key agreement, HKDF-SHA256 to derive a wrapping key, AES-256-GCM to encrypt the DEK |

Every device holds two independent key pairs — one for signing, one
for key agreement — generated locally and never transmitted anywhere.
Every environment has its own random **data encryption key (DEK)**.
The DEK itself is never written to disk in plaintext or sent anywhere
unencrypted; for each device authorized to read that environment,
Keyit stores a copy of the DEK wrapped specifically for that device's
X25519 public key. Revoking a device doesn't (and can't) reach back
and unwrap what it already decrypted, which is why revoking a device's
access is only meaningful together with rotating the affected
environment's key on the next push.

## Where your private keys actually live

<Available>macOS Keychain storage is implemented and used by default on macOS</Available>
<ProtocolDefined>native secure storage on Windows and Linux is the stated goal; today those platforms use the same restricted local-file fallback as local development</ProtocolDefined>

Private device keys are never stored inside a project's `.keyit/`
directory — that directory is public, safe-to-commit metadata only.
Where your actual signing and encryption keys live depends on the
platform:

- **macOS**: the system Keychain, via the `security` command-line
  tool (service name `dev.keyit.device-key`).
- **Everywhere else, and when explicitly requested** (`KEYIT_KEY_STORE=file`):
  a local file under `$KEYIT_DATA_DIR` (or
  `$XDG_DATA_HOME/keyit`, or `~/.local/share/keyit` by default),
  written with `0600` permissions on Unix.

If you're evaluating Keyit for a team on Windows or Linux, know that
native OS-level key storage for those platforms isn't implemented yet
— the code's own error message is direct about this: attempting
native storage outside macOS currently returns *"native key storage is
implemented only for macOS in this build."* This is tracked as an open
implementation item, not a documentation gap.
