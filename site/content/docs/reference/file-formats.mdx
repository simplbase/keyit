<Available>every path and file below is read from `keyit-cli/src/keyit_dir.rs` and `keyit-cli/src/device_key.rs`, verified by actually running `keyit init`/`env add`/`push`</Available>

Keyit splits its files into exactly two categories: one small file meant
for your project repository, and everything else, which lives entirely
outside it. There is no in-between.

## What's committed to your repository

Only one file:

```text
keyit.toml
```

```toml
version = 1
project_id = "kvp_..."
project_label = "my-project"
genesis_hash = "..."
relay_url = "https://relay.keyit.sh"
environments = []
```

This is a locator, not a secret: the project ID, a pinned hash of the
signed project-genesis record (so a tampered or substituted project
can't silently take its place), the project's configured relay, and the
environment labels registered so far. Nothing in it is useful without
the private keys and encrypted state that live outside the repository —
see [Security Model](/docs/security) for why a fully compromised
`keyit.toml` still can't decrypt anything.

Commit it like any other config file:

```sh
git add keyit.toml
git commit -m "Add Keyit project locator"
```

## What must never be committed

- **Plaintext dotenv files** — `.env`, `.env.local`, or whatever path
  you mapped with `keyit env add`. These hold your actual secret
  values in the clear on disk; that's the whole reason Keyit exists.
  Keep `.env.example` (fake/placeholder values only) for onboarding
  documentation, and gitignore everything else:

  ```text
  .env
  .env.*
  !.env.example
  ```

  Keyit does not create or edit `.gitignore` for you — add these
  lines yourself before your first commit.

- **Private device keys** — these can't accidentally end up in your
  repository even if you tried, because they're never written inside
  `project_root` in the first place. See [Where private device keys
  live](#where-private-device-keys-live) below.

- **The local `.keyit/` runtime cache** — described next. It lives
  under Keyit's data directory, not your project checkout, so a plain
  `git add .` in your project won't pick it up. Treat any `.keyit/`
  you do see inside a project checkout as a mistake to remove, not
  something to gitignore-and-forget.

## The local runtime cache (`.keyit/`)

Everything Keyit tracks about a project — beyond the one locator file
— lives under a per-project directory inside Keyit's own data
directory, resolved independently of your project's location:

```text
$KEYIT_DATA_DIR/projects/<project_id>/.keyit/
  project.toml                    <- summary metadata (id, label, relay URL)
  genesis.keyit                   <- the signed ProjectGenesis record
  membership/
    genesis.keyit                 <- the signed MembershipGenesis record
  environments/<environment_id>/
    environment.keyit             <- the signed EnvironmentGenesis record
    local.toml                    <- this device's local path mapping
    latest.toml                   <- the latest known revision id
    materialized.toml             <- the revision id last written to disk
    revisions/<revision_id>.keyit  <- local encrypted revision metadata
    payloads/<revision_id>.payload <- local encrypted payload bytes
  invites/, join-requests/, approvals/, revocations/
                                   <- signed access-lifecycle records
```

Every file in this tree is TOML — the `.keyit` extension on the record
files is a naming convention, not a distinct binary format. Byte-valued
fields (nonces, public keys, signatures) are hex-encoded strings. This
is a human-inspectable local cache of already-signed records, not
Keyit's canonical signed byte encoding — the actual signing and
verification happens in `keyit-protocol` before anything is written
here.

It's safe to read, and safe to lose: everything under `.keyit/` other
than the encrypted payload bytes for revisions you haven't pulled
elsewhere is either re-derivable from a relay pull, or specific to this
one device's local view. It is **not** the same thing as a project
backup — deleting it on your only device still means re-joining
through an invite (or a fresh `keyit init --force` as the owner) to get
back to a usable state.

## Where private device keys live

<Available>macOS Keychain storage is implemented and used by default on macOS</Available>

Independently of everything above, resolved without ever touching
`project_root`:

- **macOS** — the system Keychain, via the `security` command-line
  tool (service name `dev.keyit.device-key`).
- **Everywhere else, or with `KEYIT_KEY_STORE=file`** — a local file
  under `$KEYIT_DATA_DIR` (`$KEYIT_DATA_DIR` env override, else
  `$XDG_DATA_HOME/keyit`, else `~/.local/share/keyit`), named
  `device-signing.key` / `device-encryption.key`, written with `0600`
  permissions on Unix.

See [Security
Model](/docs/security#where-your-private-keys-actually-live) for the
platform support matrix.

## What the relay stores

<Available>read directly from `keyit-relay`'s own doc comment: "it stores signed/public metadata and encrypted payload bytes, never plaintext dotenv values or unwrapped DEKs"</Available>

The relay (hosted at `https://relay.keyit.sh`, or self-hosted) is
untrusted storage, not a trust anchor. It ever only sees:

- signed, public protocol records (project/environment genesis,
  membership, invite, join-request, approval, revocation)
- encrypted revision payload bytes and their per-device wrapped
  data-encryption keys

It never receives a plaintext dotenv value or an unwrapped encryption
key. See [Security Model](/docs/security) for the cryptography that
makes this true even if the relay operator is fully compromised.

## Local-only projects

`keyit push`/`keyit pull` publish to whichever relay the project is
configured for — see the [CLI reference](/docs/reference/cli)'s push
row for exactly how that's resolved. To keep a project entirely
offline, give it a relay URL that isn't `http(s)` when you create it:

```sh
keyit init --relay-url file://local-only
```

Any non-`http(s)` value works — nothing after the scheme is
interpreted unless you also pass `--relay-dir` to `push`/`pull` for a
filesystem-backed relay (used by this project's own local verification
scripts). With an `http(s)` relay URL configured — the default — every
push and pull talks to that relay unless the command itself overrides
it with `--relay-dir`.
